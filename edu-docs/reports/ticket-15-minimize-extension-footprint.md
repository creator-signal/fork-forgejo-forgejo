# Отчет по задаче №15: Минимизация вмешательства в код ядра

## Цель
Упростить последующие обновления (merge) оригинального кода Forgejo, минимизировав количество изменений в файлах ядра (`routers/web/web.go`, `routers/init.go` и др.).

## Что сделано

### 1. Централизация инициализации
Ранее инициализация компонентов была размазана по коду.
Мы создали единую точку входа `internal/edu/init.go`.
Теперь в ядре (`routers/init.go`) добавляется всего одна строка:
```go
mustInitCtx(ctx, edu.Init)
```

### 2. Изоляция роутинга
Логика регистрации HTTP-маршрутов вынесена из `routers/web/web.go` в отдельный файл `routers/web/edu/routes.go`.
В ядре вызов заменен на:
```go
edu.RegisterRoutes(m, reqSignIn)
```

### 3. Самодостаточные миграции
Мы отказались от использования глобальной системы миграций Forgejo (которая требует строгой версионности файлов), чтобы избежать конфликтов имен при обновлениях.

**Решение**:
*   Удалены SQL миграции из `db/migrations`.
*   Добавлены теги `xorm` в модели (`internal/edu/models.go`) для описания структуры БД.
*   Добавлена автоматическая синхронизация схемы (`db.Sync`) при старте приложения внутри `edu.Init`.

## Итоговый результат
Код расширения теперь максимально изолирован. Интеграция с ядром происходит через минимальное количество точек соприкосновения (хуки и init-функции), что существенно снижает риск конфликтов при слиянии с апстримом.
