# Погружение в архитектуру Forgejo и Образовательного расширения

Этот документ предназначен для разработчика, желающего понять внутреннее устройство проекта "с нуля". Он охватывает архитектуру платформы Forgejo и детали реализации образовательного модуля (Edu Extension).

## Часть 1: Архитектура Forgejo

Forgejo (форк Gitea) — это монолитное приложение на Go, использующее стандартную трехуровневую архитектуру (MVC).

### 1.1 Структура папок

Все начинается в корне репозитория. Вот ключевые директории, которые тебе нужно знать:

*   **`cmd/`**: Точки входа (main). Команда `web` запускает сервер.
*   **`conf/`**: Конфигурация (шаблоны `app.ini`).
*   **`routers/`**: **Контроллеры (C)**. Здесь живут HTTP-хендлеры.
    *   `routers/web/`: Обработчики HTML-страниц (UI).
    *   `routers/api/`: Обработчики REST API (v1).
    *   `routers/private/`: Внутренний API для взаимодействия с git-хуками и раннерами.
*   **`models/`**: **Данные (M)**. Структуры БД (Xorm beans) и базовые запросы.
    *   `models/db/`: Базовый движок и контекст БД.
    *   `models/user/`, `models/repo/`, `models/issue/`: Доменные модели.
*   **`services/`**: **Бизнес-логика**. "Толстые" сервисы, выполняющие сложные операции (создание репозитория с инициализацией git, отправка уведомлений и т.д.).
    *   *Правило*: Роутеры вызывают Сервисы, Сервисы вызывают Модели.
*   **`modules/`**: Утилиты и библиотеки (Middleware, Git-обертки, Логгер, Шаблонизатор).
    *   `modules/git/`: Взаимодействие с git-командой.
*   **`templates/`**: **Представление (V)**. Go-шаблоны (`.tmpl`), использующие синтаксис `{{...}}`.

### 1.2 Жизненный цикл запроса (Request Lifecycle)

Когда приходит HTTP-запрос (например, `GET /user/repo`):

1.  **Chi Router (`routers/routes.go`)**: Маршрутизатор определяет, какой хендлер вызвать.
2.  **Middleware (`modules/context/`)**:
    *   Оборачивает `http.Request` в `context.Context` (свой, "толстый" контекст Forgejo).
    *   Загружает текущего пользователя (`ctx.Doer`).
    *   Загружает репозиторий, если URL содержит `/user/repo` (`ctx.Repo`).
3.  **Handler (`routers/web/...`)**:
    *   Получает данные из `ctx`.
    *   Выполняет проверки прав.
    *   Вызывает `services` или `models` для получения данных.
    *   Кладит данные в `ctx.Data["Key"] = Value`.
    *   Вызывает рендер: `ctx.HTML(200, "template_name")`.
4.  **Template**: Генерирует HTML, используя данные из `ctx.Data`.

## Часть 2: Образовательное расширение (Edu Extension)

Мы внедрили новый функционал ("LMS внутри Git") прямо в монолит. Весь код расширения изолирован, чтобы не превращать кодовую базу в "спагетти".

### 2.1 Где лежит код?

*   **`internal/edu/`**: Ядро бизнес-логики (Service Layer, Repository Layer).
    *   Здесь интерфейсы и чистая логика, не зависящая от HTTP.
*   **`routers/web/edu/`**: Веб-хендлеры (HTTP Layer).
    *   Здесь привязка к URL и вызов сервисов.
*   **`templates/edu/`**: UI-шаблоны.
*   **`tests/integration/edu_assignments_test.go`**: Тесты.

### 2.2 Модель данных (Schema)

Мы добавили две таблицы (миграции создаются автоматически через `Xorm` при старте, если структуры описаны в бинах):

1.  **`Assignment` (`edu_assignments`)**:
    *   Описывает "Задание".
    *   Связан с `RepoID` (репозиторий-шаблон).
    *   Имеет `Title`, `Description`, `Deadline`.
2.  **`Submission` (`edu_submissions`)**:
    *   Связывает Студента (`UserID`) и Задание (`AssignmentID`).
    *   Указывает на `StudentRepoID` (личный форк студента).
    *   Хранит `Status` (started, submitted, passed, failed).

### 2.3 Ключевые сценарии

#### А. Создание задания

*(Пока только через API/Code, UI в планах)*
1.  Преподаватель создает обычный репозиторий.
2.  Мы создаем запись в `edu_assignments`, указывая `repo_id` этого репозитория.

#### Б. Студент берет задание (Join Assignment)

Файл: `routers/web/edu/assignments.go` -> `JoinAssignment`

1.  **Handler**: Получает ID задания.
2.  **Service**: `svc.JoinAssignment(ctx, user, assignmentID)`.
    *   **Проверка**: Если запись в `edu_submissions` уже есть — возвращаем её.
    *   **Форк**: Если нет — вызываем `RepoForker` (обертку над `services.ForkRepository`).
        *   Это создает полную копию репозитория-шаблона в пространстве имени студента (`student/homework-1`).
    *   **Запись**: Создаем строку в `edu_submissions` со статусом `started`.
3.  **Redirect**: Перенаправляем студента на страницу задания, где теперь видна ссылка на **Его Репозиторий**.

#### В. Сдача и Оценка (CI/CD Integration)

Файл: `internal/edu/notifier.go`

1.  Мы интегрировались в систему уведомлений Forgejo (`notify.RegisterNotifier`).
2.  Когда Runner завершает выполнение Workflow (GitHub Actions), срабатывает хук `ActionRunNowDone`.
3.  **Наша логика**:
    *   Проверяем, относится ли этот `Run` к репозиторию, который есть в `edu_submissions`.
    *   Если да — берем статус (`Success`/`Failure`) и обновляем статус в `edu_submissions`.
    *   Теперь преподаватель в таблице видит, прошел ли код тесты.

#### Г. Просмотр результатов (Instructor Dashboard)

Файл: `routers/web/edu/instructor.go`

1.  Преподаватель заходит на `/edu/assignments/{id}/submissions`.
2.  **Handler**:
    *   Проверяет права: `CanWrite` к репозиторию-шаблону (только владельцы/преподы могут видеть ответы).
    *   Загружает список ответов через `svc.GetSubmissions`.
    *   **Enrichment**: Подгружает имена пользователей (`user_model.GetUsersByIDs`), так как в таблице ответов лежат только ID.
3.  **Template**: Рисует таблицу.

## Часть 3: Как развивать проект (Советы "от себя")

Если ты полезешь в код прямо сейчас:

1.  **НЕ ИСПОЛЬЗУЙ GORM**. Forgejo использует **Xorm**. Это другой ORM.
    *   Для простых запросов: `x.Find(&beans)`.
    *   Для сложных (как у нас): мы взяли **`squirrel`** (SQL Builder), чтобы писать чистый SQL, но безопасно. См. `internal/edu/repository.go`.

2.  **Контекст — всему голова**.
    *   Везде прокидывай `ctx context.Context`.
    *   В транзакциях это критично: `sess := x.NewSession(); sess.Begin(); ...`.

3.  **Фронтенд**.
    *   Не ищи React/Vue. Тут **Fomantic UI** (форк Semantic UI) + **jQuery** (местами).
    *   CSS классы типа `ui container segment` — это база.
    *   HTML собирается на сервере.

### Твои "Читы" (Cheat Sheet)

*   **Как добавить рут?** -> `routers/web/web.go` -> ищи `func WebRoutes`.
*   **Где база?** -> Смотри `models/`.
*   **Где логика Edu?** -> `internal/edu/`.

Теперь ты знаешь систему. Код модульный, так что сломать "основной" Forgejo, меняя что-то в `internal/edu`, сложно. Удачи!
